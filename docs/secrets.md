# Secrets

Every secret the deployed services use, where it comes from, and how to replace it. This is
an operations runbook: it lists names, sources and procedures, never values. Why each secret
exists and what the application does with it is in [`security.md`](security.md). The
variables of each environment are in [`environments.md`](environments.md).

## Inventory

All of these are read by the backend, and only in `api/config.py`. The "Verify" column says
how to check a value without printing it. `<env>` stands for `dev`, `test` or `prod`.

| Variable | What it protects | Source | Scope | Verify |
|----------|------------------|--------|-------|--------|
| `SECRET_KEY` | Signs session JWTs (`api/auth/jwt.py`) and keys the CSRF token (`api/auth/cookies.py`). While `LOG_HASH_KEY` is unset it also keys the email hashes in logs. A deployed service refuses to start with fewer than 32 characters | Generated by us | One per environment | Hash compare |
| `CLOUDFLARE_ORIGIN_SECRET` | Proves a request came through Cloudflare, so `CF-Connecting-IP` can be trusted for rate limiting (`api/utils/client_ip.py`) | Generated by us | One per environment, paired with a Transform Rule on that environment's API host | Hash compare against the rule value |
| `DATABASE_URL` | Password of the `become_app` role | Railway Postgres of the environment | One per environment | `GET /api/v1/health` |
| `MIGRATION_DATABASE_URL` | Password of the owner role, used by Alembic only | Railway Postgres of the environment | One per environment | A successful pre-deploy migration |
| `REDIS_URL` | Access to the revocation and rate-limit store | Reference to the Railway Redis of the environment | One per environment | `GET /api/v1/health` |
| `EMAIL_API_KEY` | Sending mail through Resend | Resend, API Keys, permission "Sending access" restricted to the sending domain | Prod has its own key. Dev and test share one | `GET https://api.resend.com/domains` with the key. A sending-only key answers `401` `restricted_api_key`, which proves it is valid and restricted |
| `TURNSTILE_SECRET_KEY` | Server-side check of the bot-check token | Cloudflare dashboard, Turnstile, the widget | Prod has its own widget. Dev and test share one | POST to the Turnstile `siteverify` endpoint with the secret and a dummy token. `invalid-input-response` means the secret is right, `invalid-input-secret` means it is wrong |
| `BUCKET_ACCESS_KEY_ID`, `BUCKET_SECRET_ACCESS_KEY` | Read and write access to the profile-photo bucket | Railway Bucket `<env>-photos` | One per environment | S3 `list_objects_v2` with the backend's own variables |
| `BETTERSTACK_SOURCE_TOKEN` | Writing logs to a Better Stack source | Better Stack log source of the environment, EU region | One per environment | Logs from the current container arrive |
| `SENTRY_DSN` | Sending events to Sentry. The key can only write events | Sentry client key | Per Sentry project | Not needed |
| `ASSISTANT_API_KEY_OVH` | Hosted model calls on OVHcloud AI Endpoints | OVHcloud | Dev and test share one. Prod will have its own | `GET https://oai.endpoints.kepler.ai.cloud.ovh.net/v1/models` with the bearer key answers `200` |
| `ASSISTANT_LANGSMITH_API_KEY` | Sending assistant traces to LangSmith (EU) | LangSmith | Needed only where tracing is on | `GET https://eu.api.smith.langchain.com/api/v1/sessions?limit=1` with the `x-api-key` header answers `200` |
| `ASSISTANT_VECTOR_DB_URL` | Password of the read-only `corpus_reader` role on the corpus database | Reference to `CORPUS_READER_PASSWORD` on the `<env>-vector` service | One per environment that has a corpus service | The assistant answers instead of `503` |

Two variables are optional and are not covered above. `LOG_HASH_KEY` is the key for the
email tags in security logs (`api/auth/logging.py`). When it is unset the code uses
`SECRET_KEY`, so every `SECRET_KEY` rotation re-tags all later records. Set it separately
to keep tags comparable across a rotation. The other is `BUCKET_REGION`, which is not a
secret. The frontend variable `VITE_TURNSTILE_SITE_KEY` is public and does not change when
the secret rotates.

`BETTERSTACK_SOURCE_TOKEN` is not rotated in place. A new token comes only with a new source,
and on the current plan a new source can only be created in the `us_west` region. The
tokens stay as they are, an accepted trade-off. The token only allows writing logs.

`SENTRY_DSN` and `VITE_SENTRY_DSN` ship in the frontend bundle, so the DSN is effectively
public. Nothing rotates it on a schedule.

## Variables that are not secrets

`BUCKET_NAME`, `BUCKET_ENDPOINT`, `BUCKET_REGION`, `BETTERSTACK_INGESTING_HOST`,
`EMAIL_API_URL`, `API_PUBLIC_URL`,
`FRONTEND_BASE_URL`, `CORS_ORIGINS`, `TURNSTILE_HOSTNAMES` and the `ASSISTANT_*` base URLs
and model names are plain configuration. They sit next to the secrets in Railway but need no
special handling.

## Rotation rules

- Never print a value. Not in a terminal, not in a log, not in a chat.
- Set a Railway variable with `railway variable set KEY --stdin`, so the value comes from
  standard input and stays out of the shell history and the process list.
- Batch the changes of one environment. Pass `--skip-deploys` on every `set` except the
  last, so the environment redeploys once.
- Compare an old and a new value by hash, for example `shasum -a 256`, never by eye.
- Do prod only on the owner's explicit go.
- After the redeploy, check `GET /api/v1/health` answers `200`.
- Cloudflare answers `403` to the default `Python-urllib` User-Agent. Check hosts with
  `curl` or set a custom User-Agent.

## Rotation procedures

### SECRET_KEY

The application takes one `SECRET_KEY`. There is no window where two keys are accepted.

1. Generate a value: `python -c 'import secrets; print(secrets.token_urlsafe(64))'`.
2. Set it on the backend of one environment with `--stdin`.
3. Redeploy.
4. Check health, then log in once to confirm a new session starts.

Every existing session ends and every user logs in again. Links in emails (verification and
password reset) are random tokens stored hashed in the database, not JWTs, so they keep
working. If `LOG_HASH_KEY` is unset, email tags in logs change too.

### CLOUDFLARE_ORIGIN_SECRET

The variable and the Transform Rule on the environment's API host must hold the same value.
The rule runs in the `http_request_late_transform` phase and sets `X-Origin-Verify`. The API
hosts under `becomify.app` are `api` (prod), `api-atelier` (dev) and `api-harbor` (test).

1. Generate a random value.
2. Set `CLOUDFLARE_ORIGIN_SECRET` on the backend with `--stdin`.
3. Redeploy.
4. Update the rule of that host (a `PATCH` on the rule) to the same value right away.
5. Compare the hash of the variable with the hash of the rule value.

On a mismatch requests are not rejected. Every request is keyed under one shared constant
for rate limiting instead, so a mismatch quietly degrades the limits for everyone. Keep the
gap between steps 3 and 4 short.

### Database and Redis credentials

These passwords are managed by Railway and have not been rotated yet, so this order is
untested.

1. Rotate `become_app` with the zero-downtime steps in
   [`security.md`](security.md#secrets).
2. For the owner role, change the password on the database service, then update
   `MIGRATION_DATABASE_URL`. Only the pre-deploy migration reads it.
3. `REDIS_URL` is a reference, so it follows the Redis service. Redeploy the backend after a
   change there.
4. Check health after the redeploy.

### EMAIL_API_KEY

1. In Resend, create a key with "Sending access" restricted to the sending domain.
2. Set `EMAIL_API_KEY` with `--stdin` on every environment that uses the old key. Dev and
   test share one, so set both before the next step.
3. Redeploy those environments.
4. Check the new key with `GET https://api.resend.com/domains`. The answer `401`
   `restricted_api_key` means it is valid and restricted.
5. Delete the old key in Resend.

### TURNSTILE_SECRET_KEY

The dashboard is the only way: the project's Cloudflare API token has no Turnstile
permission.

1. In the Cloudflare dashboard open Turnstile, the widget, and rotate the secret key. Keep
   the grace period, so the old secret still works while services switch.
2. Set `TURNSTILE_SECRET_KEY` with `--stdin`. Dev and test share a widget, so set both.
3. Redeploy.
4. Check with `siteverify` and a dummy token. `invalid-input-response` means the secret is
   right.

The site key `VITE_TURNSTILE_SITE_KEY` stays as it is.

### Bucket credentials

Railway can also change a bucket's secret on its own. The symptom is photos failing with
`SignatureDoesNotMatch`. Compare the backend variables with `railway bucket credentials --json`.

1. Run `railway bucket credentials --reset --yes --json -b <env>-photos -e <env>`. The old
   pair stops working at once.
2. Set `BUCKET_ACCESS_KEY_ID` and `BUCKET_SECRET_ACCESS_KEY` on the backend right away.
   They are literal values there, because a Railway reference to a bucket is not possible.
3. Redeploy.
4. Check with `list_objects_v2` using the backend's variables.

### Assistant keys

1. Issue a new key at the provider (OVHcloud or LangSmith).
2. Set `ASSISTANT_API_KEY_OVH` or `ASSISTANT_LANGSMITH_API_KEY` with `--stdin`. The OVHcloud
   key is shared by dev and test.
3. Redeploy.
4. Check with the request in the inventory table.
5. Revoke the old key at the provider.

`ASSISTANT_VECTOR_DB_URL` references `CORPUS_READER_PASSWORD` on the `<env>-vector` service.
Change the password on that service and the role together, then redeploy the backend. This
order is untested.

### GitHub Actions secrets

Replace the value in the repository's Actions secrets, then re-run the job that uses it.
Revoke the old token at the provider afterwards.
